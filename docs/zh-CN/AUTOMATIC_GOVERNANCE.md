# 自动治理

本机 Git clone 被加入 AG2C 后，兼容编程 AI 的默认施工路径就是治理流程。用户仍然只输入产品需求。

## AI 怎么进入

已安装的 Skill 会在涉及文件修改时检查 `ag2c guard status`。AG2C 通过本机 Git 配置找到外部 Manifest，AI 不需要在项目里寻找治理文件。Hook、Skill 或运行时路径失效时，先自动修复再写入。未知或不兼容的 harness 会在托盘里如实显示为未就绪。

## 首次写入之前

Skill 只读检查正式工作副本，提取预计修改路径或精确公开合同。范围不确定时使用全工程保守路由。AG2C 记录原分支和 HEAD，在外部建立任务记录与 Git worktree；返回的 worktree 是唯一施工目录。

## 施工期间

AI 可以在任务 worktree 中编辑、装依赖、构建、测试和生成产物。正式工作副本只负责最后集成。每个工程都有独立的外部策略、worktree、Ledger 和证据。

## 验证

`ag2c task verify` 不相信 AI 自报范围，而是根据实际 Git diff 再算一次。新触及的已治理路径会扩大路由并留下干预记录；未纳管路径直接失败。

只运行 Policy 中已声明的 argv Checker。失败不会被后续通过覆盖；修好后通过会记录“AI 完成纠正”。如果 Checker 自己改变了受治理内容，原验证立即过期，必须重新验证。

## 集成

`ag2c task finish` 要求最终 diff 摘要和最后一次通过验证完全一致。AG2C 在任务 worktree 提交，再按 Git 对象复核，确认正式工作副本与源 HEAD 没变，最后用 `--ff-only` 集成。提交消息只留下任务号和证据摘要，完整凭证继续保存在外部工程目录。

## 强制边界

pre-commit Guard 会拒绝从正式工作副本或非 AG2C 分支交付，并且不依赖托盘窗口保持打开。但它不是文件系统权限：如果某个 AI 完全忽略 Skill，它仍可能先把正式工作副本改脏，只是在提交时被拦住。AG2C 会把这种情况显示为异常，而不会说治理成功。

## 用户看到什么

AI 的正常回复应该先讲产品结果。托盘和只读证据只补充事实：改了哪些文件、跑过哪些检查、失败后是否纠正、拦截过什么、最终提交、合并方式和证据完整性。卡片、策略、切片和检查器选择仍是内部实现。
