# 自动治理

工程一旦纳入 AG2C，治理就是默认施工路径。用户的正常开发请求是唯一任务输入；Codex 在后台把它转换成 AG2C 使用的确定性路径和合同坐标。

## 首次写入之前

Skill 先确认本机门禁已经激活，再只读检查正式工作副本，识别预计修改路径和精确公开合同，然后启动 AG2C 任务。范围确实无法确定时使用全工程保守路由，不能根据模糊目标猜一个较小范围。

AG2C 记录原分支和 HEAD，编译首次路由，并在工程外创建 `ag2c/<task-id>` Git worktree。返回的 worktree 是唯一允许写入的位置。

## 施工期间

AI 可以在任务 worktree 中检查、编辑、安装依赖、构建、测试和生成产物。正式工作副本只作为最终集成目标，不能作为施工目录。

## 验证

`ag2c task verify` 不相信 AI 自己声明的范围，而是按实际 Git diff 重新计算。实际触及新的受治理路径时自动扩大路由，并记录一次干预。未纳管路径和治理门禁修改直接失败。

当前 Policy 只选择已经审核的 argv Checker。失败结果不会被后续通过覆盖；修复后通过会记录 `ai-correction-proven`。如果 Checker 自己改动了受治理内容，本次验证同样失败，必须对新内容重新验证。

## 集成

`ag2c task finish` 要求当前 diff 摘要与 Ledger 中最后一次通过验证事件完全一致。AG2C 在任务 worktree 提交修改后再次计算提交摘要，防止已有 pre-commit hook 偷换未经验证的内容；随后确认正式工作副本仍然干净且 HEAD 未变化，并使用 `--ff-only` 合并。任何不一致都会保留现场并阻止集成。

## 用户看到什么

Codex 的正常回复只需要说明产品结果。AG2C 只补充证据事实：是否在首次写入前接管、发生过哪些干预、验证失败和通过次数、最终提交、合并方式、清理状态以及 Ledger 是否完整。
