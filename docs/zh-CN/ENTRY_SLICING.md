# 入口切片

> 内部合同：普通用户不需要操作入口切片。AG2C Skill 会在首次写入前从正常
> 开发任务中确定这些坐标，`ag2c task verify` 再按实际 diff 重新编译。

Manifest、Policy、索引和生成的切片都位于 AG2C 外部工程目录。入口切片不要求
产品仓库保存治理文件，也不会作为托盘里的用户配置页面出现。

[English](../ENTRY_SLICING.md)

入口切片，是 AG2C 把“一次想做的修改”转换成有限责任闭包、阅读范围和验证计划的方法。它要求在动手前回答四个问题：

1. 这次变更从哪个可观察的仓库事实进入？
2. 谁拥有这个事实？
3. 哪些显式依赖或公开边界必须参与？
4. 哪些检查能够证明修改后的结果？

入口切片不是“AI 可以编辑的文件清单”。它是有理由的最小工作上下文，加上一份能够证明结果的检查计划。

## 1. 什么叫入口

AG2C 接受以下确定性坐标，顺序从最精确到最宽：

| 坐标 | 写法 | 用途 |
| --- | --- | --- |
| 已存在路径 | `target-id:path/to/file` | 修改或检查已有文件。 |
| 计划新增路径 | `target-id:path/to/new-file` | 文件创建前先判断未来归属。 |
| 公开合同 | `target-id:contract.id@version` | 修改或审查生产者与消费者交界。 |
| 全部治理区域 | `--all` | 发布基线或完整验收。 |

`--goal` 不在表里，是有意为之。目标描述可以帮助人和 AI 理解意图，但自然语言不能授予代码所有权，也不能减少必须执行的检查。

因此，不要从“我要优化登录体验”直接猜应该进入哪个模块。先把它落实为现有路径、计划路径或公开合同：

```text
宽泛目标：优化登录体验
  -> 页面改动：web:src/pages/login.tsx
  -> 会话接口：api:session.create@2.0.0
  -> 若仍不知道落点，先调查，不伪造精确路由
```

## 2. 路径入口如何展开

每个路径按下面的顺序形成闭包：

```text
精确路径
  -> 恰好一个主 Floor
  -> 路径命中的局部 Knowledge
  -> Floor 显式声明的 depends_on 依赖
  -> 所有选中卡片绑定的 checker
```

路径不必已经存在。新增文件应使用最终准备落入的路径做切片，而不是使用临时文件名。这样在创建文件之前，就能发现它没有所有者或会同时落入多个 Floor。

每个受治理文件必须恰好命中一个主要 Floor：

- 没有命中是 `unowned`；
- 命中多个是 `ambiguous`；
- 恰好一个才是 `covered`。

`unowned` 和 `ambiguous` 都不能靠“选一个看起来接近的模块”继续施工，而要进入保守路由。

## 3. 合同入口如何展开

公开合同不能只从一端证明。合同入口从绑定关系反向展开：

```text
合同 ID + 精确版本
  -> Boundary
  -> 已声明的生产者 Floor
  -> 已声明的消费者 Floor
  -> 必需的 Scenario
  -> floor / boundary / scenario checker
```

以下变化都应该增加合同入口：

- 公共请求、响应或错误结构；
- 事件消息和队列载荷；
- 数据库导出格式或发布包；
- 跨进程、跨语言、跨仓库 Schema；
- 命令行或插件接口；
- 消费者需要读取、安装或执行的制品。

如果同一任务既改实现又改公共形状，应同时传路径和合同，不能二选一。

## 4. 保守回退的准确含义

AG2C 的核心裁决规则是：

> 不确定性只能扩大读取和验证范围。

以下情况会进入 `conservative`：

- 入口路径没有主 Floor；
- 入口路径同时属于多个 Floor；
- 公开合同没有精确版本绑定；
- 已同步的 Knowledge Anchor 检测到引用过期或事实冲突；
- 一次任务的实际路径覆盖了某个目标至少一半 Floor，且不少于两个 Floor；
- 任务开始后项目的 Policy 或 Manifest 发生了变化。

保守回退会选择受影响目标下的全部 Floor，以免漏检。但它不会授权修改全部 Floor。

这是必须保持的区分：

```text
验证范围扩大 != 修改权限扩大
```

实现仍应保持为完成目标所需的最小修改。扩大的是需要阅读、复核和执行检查的范围。

## 5. 切片和正文装载必须分两步

一份好的切片应该很小。AG2C 返回：卡片身份、摘要、选中原因、下一步引用和检查计划，而不是把所有治理正文、源码符号和历史记录一次性塞进上下文。

正确工作方式是：

```text
第一阶段：切片
  确定责任、边界、引用和检查

第二阶段：按需装载
  只打开选中引用和完成任务所需的真实源码
```

这样每一份进入 AI 上下文的材料都有明确原因，也避免一个公开合同把整个项目文档全部带入。

## 6. 常见任务怎么选入口

### 修改已有文件

```bash
ag2c slice --path api:src/http/orders.py --goal "增加取消原因"
```

### 新增文件

文件还不存在时，直接使用计划中的最终路径：

```bash
ag2c slice --path api:src/http/cancellation.py
```

### 修改公开 API

```bash
ag2c slice \
  --path api:src/http/orders.py \
  --contract api:orders.cancel@2.0.0
```

### 同时修改两个仓库

```bash
ag2c slice \
  --path producer:src/package.py \
  --path consumer:src/install.go \
  --contract producer:package.install@1.2.0
```

### 做发布基线

```bash
ag2c check --all
```

只有 `--all` 才有资格产生 `complete`，并且必须确保 Policy 中的所有 checker 都实际运行且通过。

项目 Policy 根本没有某阶段 checker 时，该阶段是 `not-applicable`；Policy 已定义该阶段，但当前切片没有选中时，才是 `not-run`。

### 只有目标描述，不知道文件

不要伪造路径。先做只读调查，找出真实文件或合同，再运行切片。AG2C 会拒绝只传 `--goal`，因为“听起来相关”不是责任证据。

## 7. 怎么阅读切片结果

一份切片包含：

- `entries`：用户给出的路径和合同；
- `route.state`：`precise` 或 `conservative`；
- `fallback_reasons`：为什么扩大验证；
- `cards`：责任闭包；
- `check_plan`：由卡片选中的可信检查器；
- `slice_digest`：整个决定的稳定摘要。

每张卡都有 `selection_reasons`。如果一份上下文无法解释自己为什么被选中，应把它视为策略缺陷，而不是静默加入更多材料。

如果已选中的 Knowledge 卡片完成过同步，而它引用的文件后来发生变化，
切片会报告 `stale-knowledge:<card-id>`，并把检查范围扩大到对应目标的
全部 Floor。如果记下的文档要点和当前首行对不上，则报告
`conflict-knowledge:<card-id>`。没有显式同步过的 Knowledge 保持 `unknown`，
旧项目的路由行为不受影响。可以使用以下命令查看和同步 Anchor：

```bash
ag2c knowledge status
ag2c knowledge sync --card knowledge.worker \
  --actor codex \
  --reason "Reviewed implementation changes"
```

## 8. Floor 怎么切才合理

Floor 不是目录美化，也不是把每个文件夹都变成一层。一个 Floor 应代表真实的主要所有权和能够独立讨论的验证域。

适合拆成不同 Floor 的信号：

- 有不同维护者或发布节奏；
- 有独立构建、测试或运行边界；
- 通过公共接口交接，而不是大量双向源码导入；
- 出错时可以明确指出责任所有者。

不适合强拆的信号：

- 两个目录存在大量双向依赖；
- 只能共同构建和共同测试；
- 拆分后每个 Floor 都必须加载另一边全部知识。

这类情况应暂时保留一个真实 Floor，再用更窄的 Knowledge 做局部导航。

## 9. 推荐建模顺序

接入一个现有项目时，按以下顺序：

1. 声明目标仓和 governed roots。
2. 建 Floor，直到每个受治理文件都有唯一主所有者。
3. 为 Floor 接入项目真实测试和构建。
4. 只在局部导航确实有价值时增加 Knowledge。
5. 建模真正的公开 Boundary 和生产者/消费者关系。
6. 绑定精确合同 ID 与版本。
7. 增加真实消费者 Scenario。
8. 下层状态有意义后，才使用 `--all` 做完整验收。

不要一开始写几百条规则或大段 Knowledge。先建立“唯一所有权 + 真实检查”这条骨架，系统才会产生有效信号。

## 10. 反例

不要：

- 因为 Floor 标题和任务描述相似就选择它；
- 项目已有独立责任域后仍用一个全局 `src/**` Floor；
- 用重叠 scope 掩盖归属冲突；
- 用生产者单测冒充消费者兼容证据；
- 因验证范围扩大就顺便修改无关 Floor；
- 用 `latest` 代替公开合同精确版本；
- 把可执行命令藏在 Knowledge 正文里；
- 把索引无 finding 表述为产品完整通过。

## 11. 开工前检查表

- [ ] 每个入口都有目标 ID，并使用精确路径或精确合同版本。
- [ ] 路由是 precise，或者每条 fallback reason 都已经理解。
- [ ] 选中的 Knowledge 足够局部，只用于导航当前代码。
- [ ] 公开变化包含生产者、消费者和场景。
- [ ] Check plan 使用项目真实命令，而不是占位命令。
- [ ] 扩大的验证范围没有被误解为扩大修改权限。

## 12. 收尾检查表

- [ ] 最后一次源码变化后重新构建索引。
- [ ] 使用相同入口重新编译切片。
- [ ] 执行切片选中的检查。
- [ ] 需要完整验收时运行 `ag2c check --all`。
- [ ] 验证 Ledger 哈希链。
- [ ] 报告每个未运行阶段，不把 `not-run` 写成通过。
